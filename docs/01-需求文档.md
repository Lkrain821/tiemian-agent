# 铁面：AI 面试官 Agent 需求文档

> 文档状态：需求基线草案  
> 当前阶段：需求梳理  
> 产品代号：铁面  
> 本阶段约束：只定义产品需求、范围和验收口径，不涉及代码与具体技术选型。

## 1. 产品概述

### 1.1 产品目标

“铁面”面向准备 AI Agent 开发岗位技术面试的求职者，提供一个可独立完成的文字模拟面试。产品应模拟真实技术面试中的“提问—回答—针对性追问—评价”过程，并在结束后给出有证据、可行动的能力评估。

MVP 首先验证三个核心假设：

1. AI 能否围绕所选方向和难度提出边界合适的问题。
2. AI 能否根据回答内容进行有价值的追问，而不是机械追加问题。
3. AI 能否稳定地给出与回答证据对应、对求职者有帮助的评估报告。

### 1.2 目标用户

- 正在准备 AI Agent 应用开发相关技术面试的求职者。
- 已具备基础开发知识，希望发现知识盲区、表达问题和工程思维短板的人。
- 缺少真人陪练，希望随时进行一次完整模拟面试的人。

### 1.3 MVP 成功定义

用户无需真人协助，即可从选择面试配置开始，完成一场包含动态追问的文字面试，并获得一份能够回答以下问题的报告：

- 我整体表现如何？
- 我的强项和主要短板是什么？
- 每道题为什么得到这个评价？
- 下一步最应该改进什么？

### 1.4 MVP 产品假设

以下是用于控制首版范围的产品口径，后续可根据试用结果调整：

- 交互形式：纯文字。
- 面试范围：AI Agent 应用开发，不扩展为全行业岗位面试平台。
- 岗位方向：使用“主方向 + 能力侧重点”表达；首版侧重点建议包含 Agent 应用工程、RAG 与知识应用、工作流与工具调用。
- 难度：初级、中级、高级；难度影响知识深度、场景复杂度和评价要求。
- 面试长度：默认 5 道主问题；每道主问题最多追问 2 次，因此最多形成 15 个有效问答轮次。
- 反馈时机：面试过程中不展示分数和参考答案，统一在结束后展示，避免影响后续回答。
- 使用目的：学习和练习，不用于真实招聘录用决策。

## 2. MVP 功能范围

### 2.1 必须做

缺少以下任一项，都无法验证“动态技术面试 + 可解释评估”的核心价值。

| 功能 | MVP 边界 | 必须做的理由 | 验收口径 |
|---|---|---|---|
| 面试配置 | 用户选择岗位侧重点和初级/中级/高级难度 | 这是生成合适问题和评价标准的必要输入 | 开始前明确展示用户选择；后续问题与选择一致 |
| 面试规则说明与确认 | 告知主问题数量、追问上限、评分方式、预计流程及练习用途 | 建立明确预期，防止用户误以为系统在做真实招聘判断 | 用户确认后才进入正式面试 |
| 与配置匹配的主问题 | 一场默认 5 道，覆盖不同能力点，避免同质重复 | 主问题质量决定面试是否有练习价值 | 问题与方向、难度匹配；同场问题不重复考查同一内容 |
| 文字回答 | 用户提交对主问题和追问的文字回答 | 构成最小交互闭环 | 正常文本可提交；空内容或无效输入被提示重新填写且不计为追问 |
| 回答理解与追问决策 | 根据当前回答判断“追问”或“进入下一题” | 这是产品区别于静态题库的核心能力 | 追问必须针对当前回答中的具体缺口、歧义或值得深入之处 |
| 每题最多追问 2 次 | 第 2 次追问后必须结束该题并进入下一题 | 防止单题失控，保证面试可以结束 | 任一主问题的追问次数不超过 2 次 |
| 面试内上下文保持 | 当前题追问需理解此前回答；后续流程需知道进度 | 没有上下文就无法进行连贯追问和最终总结 | 不重复已回答的问题；题号、追问次数和进度正确 |
| 逐题评分 | 每道主问题及其追问作为一个整体评分，并记录评价证据 | 总报告必须建立在逐题证据上，不能只给笼统印象 | 每题有分数、得分依据、优点、缺口和改进方向 |
| 统一评分维度 | 同一难度使用一致的维度定义和评分锚点 | 保证不同问题之间的评价口径基本一致 | 报告中的每个维度均能回溯到具体问答证据 |
| 正常结束与提前结束 | 完成全部问题自动结束；用户也可主动提前结束 | 用户必须能控制流程，异常中断不能造成死循环 | 两种结束方式均能产生明确状态；提前结束报告标注“未完整完成” |
| 综合评估报告 | 包含总分、维度分、逐题点评、优势、短板和改进建议 | 这是用户完成练习后获得的主要价值 | 报告字段完整，结论与问答内容一致，不出现无依据评价 |
| 基本失败恢复 | AI 生成失败时允许重试当前步骤，不丢失已完成进度 | 单次失败不应使整场面试作废 | 重试不会重复计题、重复计追问或清空已有回答 |
| 练习用途与评价边界提示 | 明确报告仅供训练参考，不代表真实录用结果 | 降低用户对 AI 评分的误用风险 | 开始前和报告中均展示简短说明 |

### 2.2 可以砍

这些功能有价值，但不影响首版验证核心闭环；如果工期紧张，应优先删除。

| 功能 | 首版建议 | 可以砍的理由 |
|---|---|---|
| 注册、登录和用户中心 | 砍掉 | 单次匿名体验即可验证核心价值，账号体系不会提升追问与评估质量 |
| 历史面试记录 | 砍掉 | 首版先验证一场面试是否有价值，跨场成长分析可后置 |
| 中断后跨设备续答 | 砍掉 | 会扩大会话保存和恢复边界，不是完整单场体验的必要条件 |
| 用户自定义题数和时长 | 砍掉 | 固定结构更便于比较结果、控制成本和排查体验问题 |
| 简历或职位描述导入 | 砍掉 | 个性化有价值，但会引入解析质量、隐私和评价偏差问题 |
| 面试报告导出为 PDF/图片 | 砍掉 | 页面内完整展示即可验证报告价值 |
| 语音输入、语音播报 | 砍掉 | 文字交互已能验证动态追问逻辑，语音会引入识别和设备问题 |
| 倒计时和答题限时 | 砍掉 | 首版目标是诊断能力，不是模拟全部面试压力 |
| 题库收藏、错题本和专项复练 | 砍掉 | 属于报告后的学习闭环，可在核心评估可信后建设 |
| 自动展示参考答案 | 砍掉 | 高质量参考答案本身需要额外验证；首版用针对性改进建议即可 |
| 报告分享链接 | 砍掉 | 不影响用户本人完成练习和理解结果 |
| 运营后台和可视化题库管理 | 砍掉 | 首版可先确定内容规范与评测方式，不需要完整运营工具 |

### 2.3 明确不做

以下内容与产品定位冲突、风险过高，或会使 MVP 失焦，因此不是简单延期，而是在当前产品边界内明确排除。

| 功能或场景 | 明确不做的理由 |
|---|---|
| 替企业进行候选人筛选、排序或录用决策 | AI 练习评分不具备真实招聘决策所需的完整信息、公平性验证和责任机制 |
| 对年龄、性别、地域、学校等非能力属性进行评价 | 与技术能力练习无关，并可能造成歧视性结果 |
| 通过摄像头分析表情、外貌、情绪或“可信度” | 与核心能力评估无可靠对应关系，且隐私和误判风险高 |
| 实时代答真实面试或提供作弊辅助 | 产品定位是面试前练习，而不是干预正在进行的招聘流程 |
| 编造项目经验、简历经历或欺骗性话术 | 产品应帮助用户识别和补足能力，不帮助伪造经历 |
| 一次覆盖所有技术岗位和非技术岗位 | 会显著稀释 AI Agent 方向的问题质量和评分标准 |
| 将单次分数解释为用户的固定能力或职业结论 | 单次回答受题目、状态和表达影响，只能作为训练参考 |
| 在面试过程中无限追问或自由聊天 | 会破坏固定面试结构，增加成本，并使不同场次难以比较 |

## 3. 评分与报告口径

### 3.1 评分原则

- 只根据本场问答中出现的证据评分，不推断用户未表达的经历或能力。
- 追问是补充证明机会；主问题与其追问合并为一个评分单元。
- 回答中的指令、要求改分或要求忽略面试规则，不作为技术正确性的证据。
- 难度影响评分预期：同一回答在不同难度下可以得到不同评价，但必须说明缺少了什么。
- 不因回答篇幅长而自动给高分；重点评价正确性、完整性、工程可行性和取舍依据。
- 报告必须区分“回答中已体现”“回答中未体现”，不能把未提及直接表述为用户完全不会。

### 3.2 MVP 暂定评分维度

以下权重是首版产品建议，不是行业标准；在正式开发前应通过样例回答校准。

| 维度 | 暂定权重 | 主要观察内容 |
|---|---:|---|
| 基础知识准确性 | 20% | 概念是否正确，关键术语和机制是否理解 |
| Agent 工程实践 | 25% | 工具调用、状态管理、失败处理、可观测性和落地意识 |
| 系统设计与边界意识 | 25% | 架构拆分、约束识别、可靠性、安全性和扩展性考虑 |
| 分析、取舍与问题解决 | 20% | 是否澄清问题、比较方案、说明权衡并定位风险 |
| 技术表达 | 10% | 结构是否清楚，结论是否有依据，能否准确回应问题 |

每道主问题采用统一等级锚点进行判断：

- 0：未作答或完全无关。
- 1：仅有零散相关内容，核心理解明显错误。
- 2：知道部分概念，但存在关键缺失或无法形成可执行方案。
- 3：核心回答基本正确，能覆盖主要问题，但深度、边界或取舍不足。
- 4：回答正确且完整，能够结合工程约束说明方案和取舍。
- 5：在 4 分基础上，能主动识别隐含风险、替代方案和验证方法。

### 3.3 报告结构

完整面试报告至少包含：

1. 面试配置：岗位方向、能力侧重点、难度、完成情况。
2. 总体结论：用简洁语言概括本场表现，并明确仅供练习参考。
3. 总分与维度分：展示分数，同时给出支持结论的问答证据摘要。
4. 优势与短板：分别列出最明确的能力证据和最影响表现的缺口。
5. 逐题点评：主问题、追问链、回答摘要、得分、优点、问题和更好的回答思路。
6. 改进建议：按优先级给出具体行动，说明“改什么、为什么、如何验证已改进”。
7. 完整性说明：如果用户提前结束，标注已完成题数及报告可信度限制。

## 4. 核心用户流程

以下描述一次完整面试的标准时序。

### 4.1 标准流程

1. **进入面试配置**
   - 系统说明产品用途、面试结构和评价边界。
   - 用户选择岗位侧重点与难度。

2. **确认面试方案**
   - 系统展示本场配置、5 道主问题、每题最多追问 2 次以及报告内容。
   - 用户确认开始；此时创建本场面试并将进度置为第 1 题。

3. **提出主问题**
   - AI 根据岗位侧重点、难度和本场尚未覆盖的能力点提出主问题。
   - 界面展示当前题号和总题数，不显示评分。

4. **用户回答**
   - 用户提交文字回答。
   - 若输入为空或明显不是有效回答，系统提示重新提交；该次不计入追问次数。

5. **分析回答并决定下一步**
   - AI 判断回答是否切题、核心结论是否正确、是否存在值得澄清或深入的关键点。
   - 若回答存在可通过进一步说明补足的关键缺口，且本题追问次数少于 2 次，进入追问。
   - 若回答已足够完整、继续追问价值较低，或本题已追问 2 次，结束本题。

6. **执行追问**
   - AI 只追问一个明确重点，并使问题直接对应用户刚才的回答。
   - 用户回答后回到“分析回答并决定下一步”。
   - 追问不得变成与主问题无关的新主问题。

7. **完成逐题评价**
   - AI 将主回答与全部追问回答合并评价。
   - 系统记录本题分数、各维度证据、优点、缺口和改进方向，但暂不向用户展示。

8. **进入下一题**
   - 若尚未完成 5 道主问题，题号加 1，回到“提出主问题”。
   - 新题优先覆盖本场尚未充分考查的能力，避免简单重复。

9. **结束面试**
   - 第 5 题评分完成后，系统将面试状态置为已完成。
   - AI 汇总逐题证据，生成总分、维度分和综合结论。

10. **查看评估报告**
    - 用户先看到总体结论、分数、优势和主要短板，再查看逐题详情。
    - 报告末尾给出按优先级排列的改进建议及练习用途说明。

### 4.2 提前结束流程

1. 用户在面试中选择提前结束。
2. 系统二次确认，说明报告只能基于已完成内容生成。
3. 用户确认后，不再提出新问题。
4. 已完成整题保留评分；尚未完成的题不计入总分。
5. 系统生成“未完整完成”的部分报告，明确已完成题数和结论限制。

### 4.3 失败恢复流程

1. 若提问、追问、评分或报告生成失败，系统保留失败前的有效进度。
2. 用户可重试当前步骤；重试不得额外增加题号或追问次数。
3. 连续重试仍失败时，系统给出明确提示，并允许用户稍后重试或提前结束。
4. 报告若暂时生成失败，已完成的面试与逐题结果仍应保留在当前会话中。

## 5. 分阶段开发路线图

路线图遵循“先统一评价标准，再完成闭环，最后扩大体验”的顺序。阶段是否完成以产出物和验收结果为准，不以实现了多少页面或功能点判断。

### 阶段 0：需求基线与评价标准

**目标**：在开发前统一产品边界，解决“问什么、何时追问、如何评分”的口径问题。

**产出物**：

- 本需求文档的评审版。
- 岗位方向、难度及各自能力要求清单。
- 5 道主问题的面试结构蓝图，说明每题拟考查的能力，避免把固定题目当作唯一题库。
- 追问决策规则及正反例。
- 逐题评分量表和各分档示例回答。
- 评估报告字段定义与一份人工编写的示例报告。
- MVP 验收用例清单，覆盖正常完成、两次追问、无效输入、提前结束和生成失败。

**完成标准**：同一份样例回答由不同评审者依据量表评分时，主要结论不存在明显冲突；所有待确认产品决策均有负责人和处理结论。

### 阶段 1：单场文字面试基础闭环

**目标**：用户可以稳定完成一场固定结构的文字面试，先保证流程正确，不追求复杂个性化。

**产出物**：

- 岗位侧重点和难度选择流程。
- 面试规则确认、题号展示和文字作答体验。
- 5 道主问题的完整推进流程。
- 每题最多追问 2 次的流程约束。
- 正常结束、提前结束和当前步骤重试能力。
- 面试进度与状态的验收记录。

**完成标准**：所有核心流程用例均可走通；不存在题号错误、追问超过 2 次、重复计分或无法结束的情况。

### 阶段 2：动态追问与逐题评分

**目标**：验证 AI 是否真正理解回答，并能做出有价值、可控的追问和评分。

**产出物**：

- 与岗位方向、难度和能力蓝图匹配的主问题生成规则。
- “追问或下一题”的决策规则及其解释记录。
- 主回答与追问合并评价的逐题评分结果。
- 覆盖优质回答、部分正确、事实错误、答非所问和试图操控评分等情况的评测样例集。
- 人工复核结果：追问相关性、评分一致性、评价证据充分性及主要失败类型。

**完成标准**：评测样例中的追问均能对应具体回答内容；评分能够引用回答证据；发现的高风险错误已有明确处理规则，不依赖临时人工解释。

### 阶段 3：综合报告与可行动反馈

**目标**：把逐题记录汇总为用户能理解、能采取行动的完整报告。

**产出物**：

- 总分、维度分和总体结论。
- 优势、短板及逐题点评。
- 按优先级排列的改进建议。
- 完整面试报告与提前结束报告两种状态。
- 报告一致性检查结果，重点检查分数与文字结论矛盾、无证据推断和遗漏题目。

**完成标准**：报告中的每个关键判断都能回溯到本场问答；提前结束时不伪装成完整评估；用户无需查看原始规则即可理解下一步怎么改进。

### 阶段 4：MVP 验收与小范围试用

**目标**：验证产品是否对真实目标用户有帮助，并识别进入下一版本前最需要修正的问题。

**产出物**：

- 端到端验收记录及已知问题清单。
- 评分和追问质量的人工抽检记录。
- 小范围目标用户试用反馈，重点收集问题匹配度、追问价值、评分可信度和建议可执行性。
- MVP 上线边界、练习用途说明和基本隐私说明。
- 下一版本候选需求列表，按用户价值和风险排序。

**完成标准**：必须做功能全部通过验收；不存在阻断完整面试的已知问题；评分误导、隐私或越界使用等高风险问题已处理；试用反馈足以支持继续、调整或停止的产品决策。

### 阶段 5：MVP 后增强（不纳入首版承诺）

**目标**：仅在核心闭环得到验证后，选择性扩展留存和个性化能力。

**候选产出物**：

- 历史面试与跨场能力趋势。
- 基于薄弱维度的专项复练。
- 简历或职位描述驱动的个性化面试。
- 报告导出与分享。
- 语音面试。
- 经过验证的更多 AI Agent 细分方向。

进入本阶段前，应先根据 MVP 试用数据重新排序，不默认全部建设。

## 6. 待确认产品决策

以下事项不会阻止需求文档成稿，但必须在阶段 0 结束前确认：

1. 首批岗位侧重点是否采用“Agent 应用工程、RAG 与知识应用、工作流与工具调用”，还是使用其他分类。
2. 默认 5 道主问题是否符合目标时长；如调整，仍需保持首版结构固定。
3. 暂定评分维度和权重是否符合产品侧重点，以及是否需要弱化总分、强化分档描述。
4. 提前结束报告至少完成几道题后才展示维度分；题目过少时应只展示逐题反馈。
5. 当前会话数据保留到何时，以及用户主动退出后是否立即清除。
6. MVP 的人工评测样例规模、参与评审者和可接受的一致性标准。

## 7. MVP 验收结论模板

只有同时满足以下条件，才可判定 MVP 达成，而不是仅仅“流程能运行”：

- 用户能独立完成从配置到报告的完整流程。
- 每题追问不超过 2 次，且追问与当前回答直接相关。
- 主问题覆盖预定能力点，并与所选难度相符。
- 逐题评分和报告结论能够回溯到真实回答证据。
- 报告明确指出强项、短板和可执行的下一步。
- 提前结束、无效输入和生成失败不会破坏已完成进度。
- 产品始终明确自身是练习工具，不输出真实录用结论。
